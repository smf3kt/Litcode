# W12 project-declared MCP servers: admission, not configuration

Status: verified finite admission chain. Date: 2026-10-12.
Task: a server named by a settings file the checkout owns -> it is a decision rather than a setting -> it stays pending until the person answers -> an approved declaration connects, a rejected one is never asked about again -> the answer covers the exact declaration it was granted for and the checkout it was made in -> a store that cannot be read admits nothing.

Classification: copy of the decision model, rewritten onto this runtime's storage and answering surface. The recovered product keeps the answers as two name lists inside the merged settings (`enabledMcpjsonServers`, `disabledMcpjsonServers`) plus a blanket switch; this port keeps one record per server instead, in `mcp-approvals.json` under the user directory, and reads the blanket switch from the user layer with the same precedence. Owned decisions, marked as such:

- **Fingerprint instead of name.** The recovered lists match on the name alone (`OHt(r,e)`), so an approved server whose command line is later edited keeps its approval. A checkout can rewrite its own settings file between runs, so this port stores the canonical digest of the declaration alongside the answer; a changed declaration reads `declaration-changed` and is held again. This is the recovered "a decision is a decision about something" intent made structural, and it is why the reason distinguishes `unapproved` from `declaration-changed`.
- **Workspace key instead of a settings list.** The recovered answers are settings, so they are naturally per-scope; a single store file is not. Entries are therefore keyed by the real path of the workspace, and a save carries the other workspaces' entries over unchanged, so an answer given in one checkout cannot admit the same server name in another.
- **A file the checkout cannot write.** The recovered persist target is `.claude/settings.local.json`, inside the workspace; this runtime has no project-local settings file it writes, so the store is a user-directory file created `0o700` with a `0o600` temporary file renamed into place. Nothing about the answer is under the project's control, which is the property the recovered dialog's trust-gated branch is protecting.
- **`approveAllProjectMcpServers` is refused from the project layers.** The recovered switch is a user setting, but the code that reads it is careful in a way worth matching: the scope walk skips a scope whose gate is closed, so the product never honours a switch from a scope it has decided not to trust. This runtime has no scope gates, so the port takes the stricter reading - only the user layer, or a settings file the person named themselves, may set the switch, and a workspace that sets it raises a `ConfigError` naming the file instead of being quietly ignored or quietly obeyed.
- **A failed save is reported, not thrown.** The recovered `persistFailed` notice is reproduced as one stderr line and a non-zero exit, only when nothing was written, which is why `recordMcpApprovals` is documented as throwing deliberately.

Not ported, with reasons. The interactive dialog is not ported: this runtime has no dialog subsystem, so the question is asked on stderr with the two command lines that answer it, and the answering action records the declaration and starts nothing - the chain from declaration to connection is closed by the next run, which is the same information the dialog collects. The two automatic approval routes (`bypass` and `non_interactive`) are deliberately not ported: both are gated on a `projectSettings` capability this runtime does not have, and the nearer equivalent it does have - the permission mode - is settable by a project's own settings file, so porting the `bypass` route alone would let a checkout approve itself. For the same reason the scope walk in `G8t` is not ported: it reads the enabled list and the switch out of the project and local scopes whenever their gates are open, and this runtime has no gate to consult. The plugin-contributed half of `NMr` (servers contributed by installed plugins) is not ported because plugin-declared servers are a separate surface this package does not touch, and the background-job blocking in `tNo`/`x`/`_` has no counterpart here: this runtime has no attachable job records. The name-resolution suffix module is cited for the waiting text only; the suggestion machinery it wraps (`wse` with `maxEditDistance: 2`) already exists in this runtime and was ported earlier. ## Contract and boundaries

A server declared by the workspace's own `.harness/settings.json` or `.harness/settings.local.json` is never connected while it has no answer for its exact declaration: its name is removed from the configuration the runtime dials and it is kept aside with the reason it is held. `--approve-mcp-server NAME` and `--reject-mcp-server NAME` record the answer for the current declaration without starting anything, refuse a name the project does not declare, and refuse a name given to both at once. Both need a project configuration, so they are unavailable with `--resume` and `--demo`. A rejected server is not connected and is not asked about again; a rejection is nevertheless an answer for one declaration, so editing it raises the question again instead of staying declined. An answer given in one workspace never admits another, and a change to a declaration of an approved server holds it again. The user's own `approveAllProjectMcpServers` admits every declaration in the workspace without recording anything, and an answer the person already gave still outranks it. A store that cannot be parsed admits nothing and says so on the same line as the hold; a store that does not exist is a machine that has answered nothing and is not reported as a failure. A save that cannot be written prints that the choice was not saved and that the question will return, sets a non-zero exit code, and leaves the previous answers intact. The hold is part of the session snapshot, so a resumed session still reports which names are held and why.
