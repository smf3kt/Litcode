Classification: copy of the verification rule and of the two failure behaviours, placed in one shared writer. The recovered code has the verification inline in its text writer and a separate staging-path chooser for the sandbox case; this runtime has four writers of its own, so the rule is ported once into `src/atomic-write.ts` and the two that write workspace file content - `src/tools.ts` for `write_file`/`edit_file` and `src/notebooks.ts` for `notebook_edit` - delegate to it. `src/checkpoints.ts` and `src/tasks.ts` keep their own writers: they write harness-owned state under a lock with transaction semantics, `checkpoints.ts` already carries `verify`/`committed` hooks and a directory sync, and giving them a content-verification rule of this shape would assert something different about files nobody hands in. Owned decisions, marked as such:

- **The measurement is taken on the descriptor, not on the path.** The recovered code stats the path after the write; here the size comes from `fstatSync(fd)` on the file that was just written, before it is closed and before it is renamed. That is the same number read from a handle that cannot have been swapped underneath the writer, and the later `renameSync` is what makes the name point at it.
- **The identity checked is the target directory's.** The recovered check compares the identity of the sandbox staging directory, which the writer may have chosen far from the target. This writer always stages beside the target, so the directory worth identifying is the one the rename will land in; it is identified before the temporary file is created and checked again immediately before the rename.
- **The unsupported-flush tolerance is by error code.** The recovered code notices the failure and carries on; here the specific errno set (`ENOTSUP`, `EINVAL`, `ENOSYS`, `EOPNOTSUPP`) is tolerated and every other flush failure still fails the write, because a flush that fails with `EIO` is a real problem and the recovered code's bare notice would have hidden it.
- **The kept file is named in the error.** The recovered code logs each step and leaves the temporary file; this runtime has no writer-facing log here, so the path of the kept content is appended to the refusal itself, which is the one place a caller is guaranteed to look.

Not ported, with reasons. The sandbox staging-path chooser (`ARr`) and the tamper check on a staging directory established for a sandboxed command are not ported: this runtime has no sandbox-owned staging directory, so there is no second location and no second identity to defend - the directory identified here is the only one the write touches. The `reset()` bookkeeping that closes recorded descriptors is not ported: the identity is a value held for the duration of one write rather than a per-host registry. The verified mtime is not returned to the caller: `write_file` reports the byte count it wrote, and the local edit path re-verifies the target's identity before writing rather than comparing timestamps, so a returned mtime would have no consumer. ## Contract and boundaries

Every write of workspace file content stages the new content in a temporary file in the target's directory, flushes it, measures the bytes on the file descriptor against the bytes handed in, confirms the target directory is still the one identified when the write began, and only then renames. A short write is refused rather than renamed, so a silently truncated file never appears under the real name. A directory replaced while the write was in flight cannot receive it. When the content was written whole but could not be published - the rename failed, the size was wrong, or the directory changed - the temporary file is kept and its path is named in the error, so a retry does not have to redo the work; a write that never produced a whole temporary file cleans up after itself and leaves nothing. A filesystem that cannot flush is tolerated and noted in the design, while a flush that fails for any other reason fails the write.

## Validation

`test/atomic-write.test.ts`, 9 cases: a written file holds exactly the bytes handed in and leaves no temporary file; the verified size is the UTF-8 byte length rather than the character count; a new file takes the requested mode and an overwrite takes the caller's; an overwrite replaces the content wholesale so no tail of a longer file survives; missing parent directories are created; a directory that is no longer the one identified is refused while `directoryIdentity` of a missing directory raises `ENOENT`; content that cannot be published is kept, named in the error and still holds its bytes in the target's directory; a write that never began leaves nothing behind; and a labelled write that cannot create its temporary file leaves nothing behind.

`test/tools.test.ts` adds one integration case over the tool layer: a multibyte `write_file` lands the exact bytes and the exact byte count on disk, an `edit_file` that shortens a file leaves no tail, a non-regular target is refused before any write is attempted (which is why the kept-content refusal is covered at the writer rather than at the tool), and no temporary file is left in the workspace.

No new CLI smoke driver was added. `test/tools.test.ts` already exercises `write_file` end to end and asserts the no-leftovers property, the two behaviours that changed are only observable from inside the write (a short write cannot be provoked on this filesystem, and a directory replaced between two syscalls cannot be scheduled from a driver), and the third is covered by the writer's own tests - so a driver would repeat a passing check without reaching anything new.
