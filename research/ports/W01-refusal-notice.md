# W01 model refusal: the notice and its journal record

Status: verified finite refusal-notice chain. Date: 2026-10-12.
Task: a streamed assistant message whose stop reason is a refusal -> the policy category and explanation are read from the provider's stop details -> the turn records a warning naming the refusing model, the request id and those details -> the tool calls in that message are not run -> the turn ends on the refusal reason instead of another model request.
Entry: no flag; the behaviour is unconditional and inert when the provider never refuses.

Classification: copy of the detection and of the no-fallback record shape, placed where this runtime already owns its journal. The extractor is rewritten to this product's own names and the record is a new `refusal` journal kind holding `model`, an optional `category`, an optional `explanation` and an optional `requestId`, which is the recovered no-fallback shape minus the fields that only exist to support retraction (`content` becomes the warning text this runtime prints, `level:"warning"` is the status line, and `uuid`/`timestamp` come from the ordinary journal envelope). Owned decisions, marked as such: the recovered condition also requires a message-level `isApiErrorMessage` flag that a streamed SDK message does not carry here, so this runtime keys on the stop reason alone - slightly broader, and inert unless a provider actually refuses; and the explanation is flattened to one line and bounded before it is journalled, because journal records reject control characters and the recovered explanation is free text.

Not ported, with reasons. The same-model retry is not ported: the recovered path re-sends the refused turn once, notes in the notice that it is continuing, and counts the skipped and interrupted tool calls for telemetry. This runtime ends the turn instead, so the retry's notice text is deliberately not reused (printing "continuing once" while not continuing would misreport). The fallback chain is not ported: `k_n` plus the consent prompt, the arming state and the fallback-credit handling are a separate subsystem that would need its own package and its own user decision, and the corpus review records the per-OS policy and consent surfaces separately. The retraction of the refused turn is not ported, which is why `refusedUserMessageUuid` and `retractedMessageUuids` have no counterpart here: nothing in this runtime edits the transcript in place. Skipping the tool calls owed no new code: the existing turn loop already refuses to run tools when the stop reason is not `tool_use` and writes an error result naming the stop reason, which the same recovered module does by materializing the skipped calls with a denial kind. ## Contract and boundaries

When a response's stop reason is a refusal, the turn appends one `refusal` record carrying the model, the policy category and the explanation when the provider supplies them, and the request id when it is known; it prints one warning line with the same detail; it never runs that message's tool calls and never issues another model request for the turn. The record survives a restart: the journal schema accepts the kind with every optional field absent, so a provider that sends a refusal with no stop details still records the event, and an explanation that wraps is flattened rather than rejected. A turn that is refused while a structured-output schema is requested does not attempt schema validation, because the result reason is not a successful stop.

## Validation

`test/refusal.test.ts` covers both shapes: a refusal carrying `category` and `explanation` with a tool call attached records exactly one `refusal` record with all four fields, returns reason `refusal`, calls the provider once, never executes the tool, and still pairs the skipped call with an error result so the journal replays; a refusal with `stop_details: null` and no message id records `{kind:'refusal',model:'fixture'}` only, and an explanation containing a newline, a tab and a NUL is stored flattened on one line. Both cases reopen the session and re-read the record.

`npm run smoke:refusal-cli` drives the real CLI against an owned loopback SSE gateway that emits a `message_delta` whose stop reason is `refusal` with `stop_details`, after a text block and a `read_file` tool call. In source and compiled modes it asserts the result reason is `refusal`, exactly one model request was made, the workspace file was never read, the stderr line reads `model refused this request (cyber): Cyber policy category.`, and the journal holds one `refusal` record `{model:'fixture/refusal',category:'cyber',explanation:'Cyber policy category.',requestId:'msg_refusal_fixture'}` plus one error tool result matching `Tools skipped because model stopped with refusal`. The CLI's generic non-`end_turn` exit code of 2 is asserted rather than changed.
