## Contract and boundaries

A connected dynamic catalog keeps no stale inventory across a notification: the notification marks the server dirty and starts one background refetch that runs on the catalog's serialized queue, so it can never interleave with an explicit `mcp_refresh`, discovery or pinned-metadata check. `mcp_tool_search` and `mcp_tool_call` therefore observe the post-change catalog without issuing a discovery refresh of their own, and a pinned publish snapshot keeps its original schema (only the private catalog changes). A server that keeps changing during a pass costs one follow-up pass per notification burst, not one per notification. A failing background pass is swallowed, leaves the server dirty and surfaces only if the next explicit use cannot refresh it; the connection stays usable. `close()` and an aborted connection signal stop the background work; no timer is created, so nothing keeps the process alive.
