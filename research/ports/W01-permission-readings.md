## Contract and boundaries

When a shell tool is called with a `command` string and the policy contains at least one rule that constrains a command, the decision is computed for the literal text and then for every reading of it. A denial reached from any reading denies the call, and the denial names the reason as an alternate reading rather than a literal match, so the caller can see why a command whose surface text looked allowed was refused. If every reading is permitted and the set is complete, the ordinary decision stands. If the set is incomplete, or if any reading demands approval, a decision that would otherwise have been an allow becomes an ask instead: an unexpandable command is never waved through on the strength of the text alone.

A tool rule with no `command` constraint cannot depend on how the shell reads the line, so nothing changes for it; this is what keeps the default policy, `mode`-based prompts and every existing `path` rule behaving exactly as before. A baseline denial is returned unchanged and is never softened by a later reading. `bypass` keeps its meaning: denials still stand, and incompleteness does not manufacture a prompt.

## Validation

`test/shell-permissions.test.ts` covers the reading set (`echo 'denied'` yields the de-quoted form, `true; rm -rf /` yields the segment, `echo $(cat key)` yields the substitution body, and a substitution, a variable, a glob, a leading tilde or an over-limit line is reported incomplete and bounded) and the invariant (a rule on `echo denied` denies `echo 'denied'`; a rule on `rm -rf *` denies `true; rm -rf /tmp`; a rule on `*curl*` denies `echo $(curl http://x)`; an incomplete set asks instead of allowing; a reading that asks blocks a plain allow; a rule with no command constraint, a `path`-only rule, a non-shell tool, a baseline denial and `bypass` all behave unchanged).

`npm run smoke:shell-readings-cli` drives the real CLI in source and compiled modes against an owned loopback SSE gateway. One policy denies `echo denied*` and the gateway asks for `echo 'denied' > marker.txt` - the call is refused with a reason naming the alternate reading and the marker file is never created - while the control case asks for `echo fine > marker.txt` under the same policy and does run, writing the file. The second case is what makes the first meaningful: it shows the denial came from the reading, not from a blanket refusal. Two model requests per case; the driver asserts a zero exit.
