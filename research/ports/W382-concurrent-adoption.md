# W382 concurrent plugin adoption

Status: implementation and focused verification in progress. Base `e251425`. Hooks remains Partial.

## Predicate

Overlapping declarations must not create duplicate live module records or leak environments. A declaration removed while loading must not remain active after reconciliation settles, and a replacement must end with the requested module. Direct caller errors, notification exception handling and the all-load settlement barrier remain explicit contracts. Exact reconciliation order is subject to the recovered queue and caller behavior.

## Design boundary

The pre-W382 host exposed synchronous removal and retry exceptions, and its notification tests exercised synchronous listener reentry. The source's `kVo`, `CVo`, `TVe` and `MVo` instead submit asynchronous work to one `NDe` queue. `plugins.ts` and `interactive.ts` await adoption; `config.ts` returns its Promise and catches background startup failures; the editor waits on `pluginHooksModulesSettled`. The source-shaped adapter snapshots each submitted declaration list, queues the entire reconciliation with the already copied `NDe`, and keeps that call's original error in its returned Promise. Notification delivery itself remains synchronous, and a listener's new reconciliation queues behind the current one. Consequently removal and retry errors change from synchronous throws to Promise rejections, and a caller must not wait for a queued reconciliation from inside the operation that is blocking the queue. This includes a plugin module whose top-level initialization waits for the editor's settlement barrier. That dependency can deadlock with the source's uncancellable serial queue; the current caller search found no built-in in-process module doing so, but installed plugin files have not been exhaustively inspected. No cancellation or latest-request semantics are inferred here.

An independent read confirmed the synchronous-to-Promise change and the head-of-line wait. Its proposed latest-generation/per-name cancellation would preserve the old synchronous host timing but would replace the recovered `NDe` order; that alternative is not selected. The source-shaped queue does allow an earlier load to publish before a later queued removal, then removes it before the later call and settlement complete. Queue completion therefore must include every sibling, rather than treating `Promise.all`'s first rejection as the end of the operation.

The host still starts sibling imports concurrently inside one reconciliation. Its caller receives the first failure promptly, while the queued operation holds the next reconciliation until every sibling started by that operation has settled. The owned source regression independently reproduces duplicate `2/1`, removal `1/0`, replacement `2/1` and an early successor, while its notification-error case exposes the previous synchronous exception contract. Its fixture explicitly retires any baseline orphan between subcases; output SHA-256 `5f3bb2864dc7441924a00a982b916f904ba1a438a308802779e2818666ff05bb`. An all-settled barrier is attached even if a later notification throws synchronously. The queued operation is registered before reconciliation begins, so a listener can enqueue another operation without escaping the barrier. This preserves W378/W381's observed caller-error, ownership, notification retry and barrier contracts across the queue boundary. A wait for settlement includes queued operations already submitted and repeats if a listener submits another during the wait. This is an adaptation of `NDe` and `kVo` loading ownership, not a claim to have ported the source's complete whole-set admission or worker state. The product's installed index rejects duplicate plugin names (`src/plugins.ts` `load` lines 419-420), but the exported adoption boundary does not. A direct duplicate-name array therefore starts two loads and loses one owner. The adapter applies the same uniqueness rule before any queued reconciliation effect and rejects the duplicate declaration; an existing inventory remains untouched. This is a host boundary validation, not a claim that source `a_e` rejects such an array. The independent reviewer reproduced that leak and found a second pre-existing gap: when a removal notification throws, this host's per-record unload loop stops with later modules still live. Source `iF` [2390383,2390919) selects and removes the whole set from the inventory and retires its records before `Xye`; the host adapter defers its existing inventory notification until every selected `unload` completes, then delivers it once and propagates the notification error. It preserves pending notification state for retry. The independent repair review verifies those two findings but identifies a separate retirement exception sequence: this host deletes every owner first, so if the first `retire()` throws, a later still-live record has no removal handle. The source `iF` removes the full inventory before retiring and propagates a retirement exception; the host's per-record handles cannot be bulk-removed without a larger loader rewrite. The adapter will delete each owner only when its unload begins, preserving the original error and keeping not-yet-visited records owned for a later reconciliation. This intentionally differs from source's wholesale inventory replacement only on this unverified exceptional path. A focused fixture injects a throwing record and confirms the later owner is lost before the repair. After an independent review found the fixture had restored the first record's retirement function without calling it, its cleanup now invokes that restored function and removes its own remaining records. It does not establish what causes a real retirement to fail or prove recovery of that first environment in production. Owned source regressions independently reproduce the two original findings before repair. The three original compiled red probes remain the concurrency baseline.
