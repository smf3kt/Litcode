# W381 module ownership on notification failure

Status: main verification and independent scoped repair review passed. Base `62f7216`. Hooks remains Partial.

## Predicate

A file module published before a notification listener fails remains represented in the inventory, the direct caller observes the notification failure, and the module retains an owner that can remove it. Reconciliation of the same declaration must not load a duplicate. Removal must release the one published record and environment. Successful load/unload notification behavior remains unchanged.

## Adaptation

The source keeps published records addressable through the inventory and known-plugin state before notification; this host's registry instead needs a `LoadedChainModule` handle to remove an environment. The two notification-retry defects share a missed-notification premise across both insertion and removal: a per-module flag cannot represent a pending update once its module is removed. The host adapter now uses one inventory-scoped pending/notifying/complete state for both operations, retries it on reconciliation including an empty declaration, and preserves the source's exception propagation. A nested inventory mutation during notification must trigger another publication after the outer notification succeeds; failed publications stay pending for the next reconciliation. This is a host adaptation of the source's whole-set `isSetRecord`/`Xye` ordering, not a claim that the missing source admission queue was ported. The loader now builds that handle before publishing and gives the registry a publication callback that stores it after inventory insertion and before the existing notification. The notification exception remains visible to direct callers. On removal, the registry drops its known owner before invoking the existing unload operation, matching `CVo`'s known-plugin deletion before `iF`; the unload still removes the record, retires it, and publishes the removal in its existing order. Standalone direct-loader callers have no registry publication callback, so recovery from their own throwing listener remains a separate boundary. The source `iF` retires before notification, and a throwing retirement remains untested; no rollback contract is claimed.
