Classification: copy of the limit data with an owned enforcement rewrite. The recovered client satisfies the API contract by transforming the image; this runtime has no image codec, so it keeps the same contract at the boundary it can control. Ported as given: the 2000x2000 dimension target, the 5 MiB base64 cap, the 3932160-byte raw budget (`maxBase64Size*3/4`, and exactly the raw size whose base64 is 5242880 bytes), the refusal when the payload cannot be brought inside that budget, and the refusal wording's guidance to resize manually or use a smaller image. Not ported, marked as owned narrowings: the model-config `image_limits` branch and its 1568 floor (this runtime has no model-config image_limits source, so the resolver would be dead code), the downscale/recompress step itself (requires `Bun.Image`), webp re-encoding, BMP decode, and the clipboard transform. Over-target dimensions are reported rather than refused because the recovered 2000px figure is the many-image constraint it satisfies by downscaling, while the API accepts larger single images; refusing would reject requests the API serves. No recovered entrypoint was executed.

Bounded negative search for a portable codec: `createImageBitmap`, `OffscreenCanvas`, `getImageData`, `createCanvas`, `node-canvas`, `@napi-rs`, `resizeImage`, `scaleImage`, `maxDimension`, `jpeg-js` all have zero hits across modules/*.js; `pngjs` appears only as a packer (`packIHDR`, no `sync.read` decode path) in chunk-rr5rbabs.js; `IHDR` reads elsewhere are header-only dimension parses; `sips`, `magick` and `downsample` hits are unrelated keyword tables, a URL regexp and an HDR histogram. The recovered product therefore has no codec-free resize path to port.

## Contract and boundaries

The base64 length of an accepted image must be at most 5242880 bytes, which is exactly the raw budget 3932160; over that the read fails before any block is produced, with the encoded and raw sizes and manual-resize guidance. Header-verified dimensions above 2000x2000 do not fail: the native block is produced, `metadata.exceedsDownscaleTarget` is true and the summary states that the 2000x2000 downscale target was not applied. `metadata` now also carries `base64Bytes` for every image. Existing bounds are unchanged: 10 MiB per file, extension/detected-type agreement, PDF page selection, workspace confinement, and byte-preserving journal resume. The clipboard path keeps its 10 MiB/5 s bounds and private attachment store; a captured PNG over the base64 budget now fails its post-publish media validation and the attachment is removed again.
